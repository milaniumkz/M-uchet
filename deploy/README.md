# Подготовка собственного сервера

Это конфигурация для проверки и будущего размещения. Пользовательский сервер ещё не предоставлен; production не развёрнут. Все команды ниже выполняются на выбранном сервере после настройки домена, хранения секретов и резервного копирования. Публичная регистрация закрыта независимо от флагов окружения.

## Образ

Сначала в корне репозитория соберите клиент: `make build-web`. Затем:

```sh
docker build -f deploy/Dockerfile -t muchet:reviewed .
```

В управляемой облачной среде при сборке необходим её TLS CA. Сохраняйте настройки прокси Docker и проверку TLS:

```sh
BUILDX_CONFIG=/workspace/M-uchet/.runtime/buildx docker build \
  --secret id=proxy_ca,src="$CODEX_PROXY_CERT" \
  -f deploy/Dockerfile -t muchet:local-check .
```

Node24 и PostgreSQL17 закреплены digest. Образ содержит API, миграции, справочник счетов и готовый web-клиент. Контекст допускает только эти файлы; `.env`, `.runtime`, архивы пользователя, тестовые пароли и локальные базы не попадают в образ. Сессионный CA монтируется только на шаг установки зависимостей, не копируется в образ. API работает от uid1000, файловая система образа read-only; загрузки сохраняются в отдельном томе. Корень `/app/data` не должен быть заменён каталогом, недоступным uid1000.

## Конфигурация

`deploy/compose.yaml` принимает переменные-пути:

- `MUCHET_IMAGE`: проверенный локальный тег/образ с неизменяемым digest.
- `MUCHET_DB_ADMIN_PASSWORD_FILE`: отдельный файл пароля администратора PostgreSQL.
- `MUCHET_DB_PASSWORD_FILE`: файл пароля прикладной роли muchet.
- `MUCHET_DATABASE_URL_FILE`: файл полного URL `postgresql://muchet:<URL-encoded-password>@db:5432/muchet`. Должен быть доступен uid1000 внутри контейнера. У локального Compose секреты являются bind mounts; настройки uid/gid секрета не заменяют фактические права файла на хосте.
- `MUCHET_PORT`: локальный порт API, по умолчанию18080.

Файлы секретов храните вне репозитория, с правами0400/0600 и подходящим владельцем. Не передавайте пароль в командной строке. Не меняйте пароль уже существующей БД простым редактированием файла: изменение секрета не изменяет пароль роли PostgreSQL.

```sh
docker compose -f deploy/compose.yaml up -d --wait
```

База не публикует порт. API слушает только127.0.0.1 хоста. Для HTTPS подготовлен `Caddyfile.example`; реальный домен и DNS потребуются при размещении. Приложение обслуживает web и API с одного origin; внешний CORS не требуется. API не доверяет произвольным X-Forwarded-For: за единственным reverse proxy лимит входа сейчас общий для пользователей этого прокси. Конкретные доверенные адреса следует настроить по фактической сетевой схеме.

Первый владелец создаётся офлайн на пустой базе из защищённого JSON через stdin:

```sh
docker compose -f deploy/compose.yaml run --rm --no-deps -T api \
  src/provision-owner.js < /secure/owner.json
```

JSON содержит login/name/password; его содержимое не выводится. Повторное начальное создание на непустой базе отклоняется. Тестовые данные в production не загружать. При обновлении миграции выполняются при запуске API; перед обновлением необходима согласованная резервная копия БД и загрузок. Откат схемы автоматически не выполняется.

## Проверка без размещения

```sh
node deploy/check-container.mjs muchet:local-check
```

Проверка создаёт отдельный проект Compose со случайным именем, новую синтетическую БД, секреты и случайный loopback-порт. После завершения удаляет только свои контейнеры, тома и секреты. Существующие данные приложения не используются. Проверяются первый владелец, закрытая регистрация, HTTP/web, точный остаток, календарь, приватный файл, перезапуск API, шифрованная копия и реальное восстановление с проверкой ошибок, офлайн-восстановление пароля, ограниченная роль БД, непривилегированный пользователь и запрет записи в образ.

Согласованное шифрованное копирование и восстановление: [BACKUP.md](BACKUP.md). Полная приёмка продукта, мониторинг, расписание/внешнее хранилище копий, проверка восстановления на целевом сервере, официальный налоговый экспорт и окончательное соответствие всем макетам ещё не завершены. Данная конфигурация не объявляет их готовыми.

Обёртки `make build-container` и `make test-container` используют тег muchet:local-check (переопределяется MUCHET_IMAGE). Первая сохраняет текущие настройки Docker, автоматически монтирует CA управляемой среды при его наличии и размещает состояние Buildx в writable .runtime. Локальная контейнерная проверка пройдена на schema21; это не развёртывание на сервере пользователя.

При первичной инициализации нового тома PostgreSQL администратор postgres и прикладная роль muchet получают разные пароли. Прикладная роль владеет только БД приложения; NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION. Инициализатор не выполняется повторно на существующих томах. Не подключайте ранее созданный том с иной схемой ролей без отдельной миграции. Скрипты db-entrypoint.sh/db-init.sql должны оставаться доступными контейнеру; они не содержат паролей.
