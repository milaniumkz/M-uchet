# M-uchet API — первый этап независимого backend

Node.js **24.x**, Fastify 5, SQLite (встроенный `node:sqlite`). Старый Firebase не используется. Все данные и файлы создаются заново. Это работающий сервер основных операций, **не завершённая миграция Flutter-приложения и не полный аналог прежней системы**.

## Запуск

```bash
cd /workspace/M-uchet/server
npm ci
npm test
HOST=127.0.0.1 PORT=8080 DATA_DIR=/workspace/m-uchet-data npm start
```

`GET /health` должен вернуть `{"status":"ok","schemaVersion":1}`. Схема создаётся идемпотентно при запуске. На диске сохраняются база, WAL и `uploads/`; процессы после восстановления облачной среды нужно запускать заново. Для локальных тестов регистрация включается только внутри тестового приложения, данные создаются во временных каталогах.

Для первоначального создания пользователей запустите API с `ALLOW_REGISTRATION=true` **только на закрытом адресе**, зарегистрируйте нужных пользователей и перезапустите без этой переменной. По умолчанию регистрация выключена. Нет стандартного пароля, встроенного администратора и тестовых production-аккаунтов. Вход принимает `login` (в том числе номер телефона) и пароль длиной 12–256 символов. Подтверждение телефона, SMS, восстановление пароля и MFA пока не реализованы.

Настройки: [`.env.example`](.env.example). При использовании файла: `node --env-file=.env src/main.js`. `DATA_DIR` разрешается относительно рабочего каталога процесса. Для постоянного сервера задайте абсолютный путь вне checkout.

## Реализовано и проверяется

- Пароли scrypt с индивидуальной солью, случайные bearer-сессии на 12 часов, хранение только хеша токена, выход и смена пароля с отзывом всех сессий.
- Компании и отдельное членство в каждой компании. Владелец компании не получает прав на другие компании. Права участников назначает только владелец; удаление членства действует сразу. Изменение владельца через API запрещено.
- JSON-справочники с явным allowlist ресурсов, серверной областью компании, пагинацией и optimistic locking. Финансовые регистры и security-коллекции не доступны через произвольный CRUD. JSON-данные справочников — гибкие метаданные; это не полная доменная валидация всех полей клиента.
- Приход партий и FIFO, резервирование без отрицательного остатка, отмена резерва, отгрузка, себестоимость и валовая прибыль. Полная оплата закрывает заказ, частичная уменьшает дебиторскую задолженность. Переплата запрещена.
- Сбалансированный неизменяемый журнал двойной записи и оборотная ведомость. Отдельные `ACCOUNTING`, `MANAGEMENT`, `BOTH`; записи BOTH включаются один раз в каждый отдельный контур. Валюта задаётся при создании компании, обмен валют не реализован.
- Обязательный `Idempotency-Key` для складских/финансовых команд; повтор того же запроса возвращает сохранённый ответ, другой запрос с тем же ключом — 409. Данные, проводки, аудит и ключ фиксируются одной SQLite-транзакцией.
- Приватные файлы до 10 MiB: загрузка и скачивание только с правами своей компании, UUID вместо пользовательского пути, скачивание как attachment/octet-stream.
- Аудит изменений и online-backup базы.

Деньги — целые **минимальные денежные единицы** (например, 100 = 1.00 KZT), количество — целые **базовые единицы товара**. Дробный товар можно учитывать только после явного выбора базовой единицы и преобразования в клиенте. Клиентские `double` нельзя пересылать без преобразования. Максимум отдельной суммы/количества — 10^12; переполнения проверяются. Себестоимость сейчас только FIFO: средневзвешенная из клиента ещё не перенесена.

## API

Контракт и примеры: [docs/API.md](docs/API.md). Токен передаётся только в `Authorization: Bearer …`, не в URL. Файлы тоже требуют этого заголовка. Пользовательский bearer нельзя безопасно подменить публичной ссылкой для стандартного Image.network без нового адаптера.

`GET /v1/capabilities` возвращает поддержанные ресурсы и права. Ошибки: `{error, requestId}`; 400 — неверные данные, 401 — нет сессии, 403 — нет права, 404 — объект отсутствует/нет членства, 409 — конфликт версии/состояния/остатка/ключа. 429 ограничивает частоту запросов. В production используйте HTTPS через reverse proxy, не публикуйте порт API напрямую.

## Размещение и резервирование

До предоставления сервера проверен запуск обычного Node-процесса, не production deployment. SQLite рассчитана на **один экземпляр API на локальном постоянном диске**. Не размещайте базу на NFS и не запускайте несколько реплик. Для масштабирования потребуется миграция хранения на PostgreSQL. Трафик и размер базы пока не нагрузочно тестировались.

На сервере: отдельный непривилегированный пользователь, Node 24, `npm ci --omit=dev`, постоянный `DATA_DIR` с правами 0700, TLS reverse proxy и process supervisor с `WorkingDirectory` каталога server. `CORS_ORIGIN` — точный origin вашего web-клиента; CORS не заменяет авторизацию. API не доверяет forwarded headers, поэтому rate limit за proxy общий по адресу proxy; настройку доверенного proxy нужно сделать по фактической схеме сервера. Не включайте безусловное доверие произвольным X-Forwarded-For.

```bash
DATA_DIR=/workspace/m-uchet-data BACKUP_DIR=/workspace/m-uchet-backups npm run backup
```

Команда копирует согласованный снимок базы через SQLite backup API. **Файлы uploads нужно копировать отдельно.** Для согласованной полной копии остановите собственный API, сохраните backup базы и uploads вместе, затем запустите API. Шифрование, внешнее хранение и расписание backup настраиваются на реальном сервере. Восстановление: остановить API, сохранить текущие данные, восстановить backup как `DATA_DIR/uchet.sqlite` и соответствующий uploads в **новый** каталог без старых WAL/SHM, проверить `/health`, вход и реальные документы. На рабочей базе ничего автоматически не перезаписывается.

## Что ещё необходимо

См. [docs/FRONTEND_BACKEND_GAPS.md](docs/FRONTEND_BACKEND_GAPS.md). Клиент по-прежнему блокирует запуск: Firebase-адаптеры ещё не заменены. Не выдавайте этот API за готовность всего приложения. Не реализованы возвраты/сторно со связью с исходной продажей, частичные отгрузки, перемещения между складами, полноценные кассовые смены, налоговые расчёты, HR, подписки/биллинг, уведомления, восстановление удалённых данных и 1С-интеграция. Наличие одноимённого справочника не означает реализации процесса. Старые Firebase-настройки, доступы и deployment workflows не восстанавливались.
